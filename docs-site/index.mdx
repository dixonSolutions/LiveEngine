---
title: "Introduction"
description: "LiveEngine is a Rust matchmaking engine plus an authenticated HTTP hub registry for Node.js and Rust services."
---

LiveEngine solves two related problems:

1. **Pairing users with capacity-limited servers.** A deterministic, in-process engine holds users and servers, evaluates requirements in both directions, and pairs users into rooms.
2. **Routing matchmaking calls across processes.** A hosted registry lets one service own internal engines and attach independently hosted hubs through a uniform, authenticated HTTP contract.

The same runtime can be embedded in a Node.js service, embedded in a Rust/Axum API, or run standalone as the `liveengine-hub` executable. Current release: **0.3.0**.

## What is in the box

| Artifact | Name | What it provides |
| --- | --- | --- |
| npm package | `@dixonsolutions/liveengine` | Rust N-API engine, TypeScript definitions, `HubClient`, and the `liveengine-hub` command |
| Cargo crate | `liveengine` | `Engine`, `rules`, and the optional Axum `HubService` |
| Cargo binary | `liveengine-hub` | Standalone HTTP host and central registry |
| Container | same image | Central registry, ordinary internal hub host, or remote service |
| Integration | Gogh Strike bridge | Optional server-side bridge from a browser game to the hub contract |
| Interface | User hub | Dependency-free browser UI with room listing, matchmaking and native ping |

The former C++/node-gyp implementation has been replaced by Rust. The existing `LiveEngine` and `NativeEngine` Node interfaces remain. Seeded sequences are deterministic within the Rust implementation, but random sequences are **not** byte-for-byte compatible with the previous C++ generator.

## Architecture

```text
                       authenticated HTTP (liveengine.hub/v1)
  application / game  ──────────────────────────────────────────┐
  server code                                                    │
        │                                                        ▼
        │  in-process                                   ┌──────────────────┐
        ├──────────────► Engine (Rust)                   │ Central registry │
        │                users + servers                 │  LIVEENGINE_TOKEN│
        │                requirements + strategies       └────────┬─────────┘
        │                                                        │
        │  HubClient                                             │ register internal
        └──────────────► ┌──────────────────┐                    │ register external
                         │ Hub host         │◄───────────────────┘
                         │ internal engines │
                         │ external routes  │──────► external hub (its own
                         └──────────────────┘        engine or custom handler)
```

- An **internal** hub is backed by an `Engine` created by the host. HTTP registrations of mode `internal` get a fresh matchmaking engine.
- An **external** hub is a route to another HTTP service. The host performs a health/contract handshake at registration time, then forwards calls.
- A **central registry** is simply a host that also holds registrations for other hubs. The same process can do both jobs.

## Delivery and platform support

```sh
npm install @dixonsolutions/liveengine   # Node.js 22+
cargo add liveengine                     # Rust 1.88+
cargo install liveengine --bin liveengine-hub
docker build -t liveengine:local .
```

Release tarballs include native binaries for Linux x64/arm64 (glibc), macOS x64/arm64, and Windows x64. Source checkouts and other platforms build with Rust 1.88+ and the platform linker. The HTTP-only client is available without loading the native addon:

```js
const { HubClient } = require('@dixonsolutions/liveengine/hubs');
```

See [Installation](/node/installation) for the platform matrix and source fallback.

## Honest scope for 0.3.0

LiveEngine is deliberately small and explicit about what it does not do:

- **Live matchmaking state is in memory.** A state file can persist registry definitions, but users, rooms, memberships and events are lost on restart.
- **Authentication is administrative.** The host verifies one bearer token, and issues single-use tickets for live sockets. A hub can verify a credential your application relays ([custom auth](/guides/custom-auth)), but there are no player accounts, authorization policy or tenant isolation. Keep tokens in server code and expose application-specific routes to clients.
- **Request timeouts do not roll back work.** An internal handler that already started continues on a blocking worker. Capacity stays occupied until it finishes. Reconcile state before retrying a mutation.
- **Schemas use JSON Schema 2020-12.** References must be local JSON pointers and are bounded.
- **Remote imports can refresh.** Set `refreshSeconds` to discover changes and mark missing entries stale.
- **Gogh Strike integration exchanges player state and events** using LiveClient with direct and relay transports.
- **Ping is a latency probe, not a matchmaking input.** Use `HubClient.ping()` or `liveengine-hub ping` to measure a hub; add your own scope/requirement rules if you want ping to influence matching.
