LiveEngine is the plumbing for live, multi-user applications, in one package for Rust and Node.js. It hosts **hubs**, keeps a **registry** of them, pairs users with a hub or with each other, and connects them in **live rooms**. Core never knows your game or app: scopes, schemas, channels and payloads are all yours, defined at runtime.

What it does:

- **Hub hosting and registry.** One service hosts many hubs behind one authenticated HTTP contract (`liveengine.hub/v1`): matchmaking engines, your own Rust handlers, or routes to hubs on other services. Run it standalone (`liveengine-hub`, the container image) or embed it in an Axum API. See [hosting](/guides/hosting) and [remote hubs](/guides/remote-hubs).
- **Nested central hubs.** Central hubs are namespaces that hold other hubs, locally or on another service, so hubs form a tree you route into by path. See [nesting](/guides/nesting).
- **Matchmaking and pairing.** Discover hubs and peers that match requirements, and pair a user with a hub or with another user, optionally waiting for a partner. Pairing returns a descriptor with a single-use ticket. See [find and pair](/guides/find-and-pair).
- **Live rooms relayed by the hub.** A client opens the room socket with its ticket; the hub relays frames, checks channels and schemas, and reports presence. See [live rooms](/guides/live-rooms).
- **Direct peer-to-peer.** For peer pairings the JavaScript `LiveClient` opens a WebRTC data channel to each peer, signalled through the hub, and falls back to the hub relay when it cannot. See [peer-to-peer](/guides/peer-to-peer).
- **Hub-to-hub links.** Two services can bridge a room over a persistent WebSocket link, with merged presence. See [hub links](/guides/hub-links).
- **Live hub lists.** Subscribe to the registry and receive a snapshot and then diffs, from a server or, with a read-only ticket, a page. See [live registry](/guides/live-registry).
- **Pluggable hub auth and accounts.** A hub can verify the player's credential before any ticket: a session of a local account, static tokens, HMAC, JWT, a webhook or your own Rust verifier. Administrators can list and kick connections and ban accounts. See [custom auth](/guides/custom-auth), [accounts and sessions](/guides/accounts-and-sessions) and [manage live connections](/guides/connections-admin).
- **Provider-hosted hubs.** Run a central hub for a customer on your service and give them one credential for that subtree only. See [provider hosting](/guides/provider-hosting).
- **A browser-facing API.** `createHubApi` gives a page pairing, renewal, seats, a hub list and sign-in, while the administrator token stays on your server. See [hub API for browsers](/guides/hub-api).

Current release: **0.5.0**.

## What works where

| Capability | Rust (`liveengine` crate) | Node.js (`@dixonsolutions/liveengine`) | Browser |
| --- | --- | --- | --- |
| In-process matchmaking engine | `Engine` | `LiveEngine` (native addon) | No |
| Host hubs, registry, nesting, links | `HubService` router, `liveengine-hub` binary | Runs the `liveengine-hub` command; no in-process host | No |
| HTTP client: register, route, discover, pair, tickets, accounts, connections | `hub::HubClient` | `HubClient` | No: keep the token on a server |
| Live registry watch | `HubClient::watch` | `HubClient.watchRegistry` | `watchHubs`, with a ticket from your server |
| Join a live room through the hub relay | `live_client::LiveClient` | `LiveClient` (Node 22+) | `LiveClient`, `connectLive` |
| Direct WebRTC data channels | No: Rust peers use the hub relay | `LiveClient` with an `RTCPeerConnection` you supply | `LiveClient`, built in |
| Hub-to-hub room links | Run by the service | Defined over HTTP (`/v1/links`) | No |
| Browser-facing pairing and sign-in routes | Write your own | `createHubApi` | `connectLive`, `watchHubs`, `hubSession` |

Hub-to-hub links are WebSocket connections between services. WebRTC is only used between JavaScript clients, and only for `peer-peer` pairings.

## What is in the box

| Artifact | Name | What it provides |
| --- | --- | --- |
| npm package | `@dixonsolutions/liveengine` | Rust N-API engine, TypeScript definitions, `HubClient`, the `live-client` and `hub-api` modules, and the `liveengine-hub` command |
| Cargo crate | `liveengine` | `Engine`, `rules`, and the optional Axum `HubService`, `HubClient` and live-room `LiveClient` |
| Cargo binary | `liveengine-hub` | Standalone host, central registry and command-line client |
| Container | same image | Central registry, ordinary internal hub host, or remote service |
| Integration | Gogh Strike bridge | A browser game paired and connected through a hub, with direct and relay transports |
| Interface | User hub | Dependency-free browser UI with room listing, matchmaking and native ping |

The former C++/node-gyp implementation has been replaced by Rust. The existing `LiveEngine` and `NativeEngine` Node interfaces remain. Seeded sequences are deterministic within the Rust implementation, but random sequences are **not** byte-for-byte compatible with the previous C++ generator.

## Architecture

```text
  your server (holds the administrator token)
        │  HTTP liveengine.hub/v1: register, route, discover, pair, tickets
        ▼
  ┌──────────────────────────────┐   remote central / external hub   ┌──────────────────┐
  │ LiveEngine service           │ ────────── HTTP forwarding ──────► │ another service  │
  │  registry + central hubs     │                                    │                  │
  │  internal hubs (engines,     │ ═══════ hub link (WebSocket) ═════ │  linked room     │
  │  your Rust handlers)         │                                    └──────────────────┘
  │  live rooms + live registry  │
  └──────────────────────────────┘
        ▲  room socket: single-use ticket, relayed frames, presence, signalling
        │
  LiveClient (browser or Node) ◄═══ WebRTC data channel (peer-peer pairings) ═══► LiveClient
```

- An **internal** hub is backed by an `Engine` created by the host, or by a Rust handler you register. An **external** hub is a route to another service. A **central** hub holds other hubs.
- Your server pairs a user and passes the descriptor to the client. The client never sees the administrator token.
- The [live architecture](/concepts/live-architecture) page follows one connection through every stage and shows which credential lives where.

## Delivery and platform support

```sh
npm install @dixonsolutions/liveengine   # Node.js 22+
cargo add liveengine                     # Rust 1.88+
cargo install liveengine --bin liveengine-hub
docker build -t liveengine:local .
```

Release tarballs include native binaries for Linux x64/arm64 (glibc), macOS x64/arm64, and Windows x64. Source checkouts and other platforms build with Rust 1.88+ and the platform linker. The HTTP-only client is available without loading the native addon:

```js
const { HubClient } = require('@dixonsolutions/liveengine/hubs');
```

See [Installation](/node/installation) for the platform matrix and source fallback.

## Honest scope for 0.5.0

LiveEngine is deliberately small and explicit about what it does not do:

- **Live state is in memory.** A state file can persist registry definitions, accounts and sessions, but users, rooms, memberships, presence and events are lost on restart.
- **Authentication is narrow.** The service verifies one administrator token, issues single-use tickets for live sockets, and can verify a player credential per hub ([custom auth](/guides/custom-auth)). Local [accounts](/guides/accounts-and-sessions) have two roles, `admin` and `user`, and no sign-up, recovery or multi-factor sign-in. There is no tenant isolation beyond [provider hosting](/guides/provider-hosting). Keep tokens in server code and expose application-specific routes to clients.
- **WebRTC is JavaScript only.** Rust services host rooms and links and join rooms with `live_client::LiveClient`, but over the hub relay; direct data channels are opened only by the JavaScript client.
- **Request timeouts do not roll back work.** An internal handler that already started continues on a blocking worker. Capacity stays occupied until it finishes. Reconcile state before retrying a mutation.
- **Schemas use JSON Schema 2020-12.** References must be local JSON pointers and are bounded.
- **Remote imports can refresh.** Set `refreshSeconds` to discover changes and mark missing entries stale.
- **Ping is a latency probe, not a matchmaking input.** Use `HubClient.ping()` or `liveengine-hub ping` to measure a hub; add your own scope/requirement rules if you want ping to influence matching.
