`HubConfig` is the runtime configuration for a hosted registry. Build it directly when embedding, or use `HubConfig::from_env()` for the standalone binary's environment contract.

## Fields and defaults

```rust
pub struct HubConfig {
    pub token: String,
    pub allowed_remote_hosts: Vec<String>,
    pub max_hubs: usize,
    pub max_request_bytes: usize,
    pub max_response_bytes: usize,
    pub max_args: usize,
    pub max_entities: usize,
    pub max_events: usize,
    pub max_generates_per_call: usize,
    pub max_inflight_calls: usize,
    pub request_timeout: Duration,
    pub rate_limit_requests: usize,
    pub rate_limit_window: Duration,
    pub rate_limit_peers: usize,
    pub max_ttl: Duration,
    pub seed: u64,
}
```

| Field | Type | Default |
| --- | --- | --- |
| `token` | `String` | empty (invalid until set) |
| `allowed_remote_hosts` | `Vec<String>` | empty |
| `max_hubs` | `usize` | `256` |
| `max_request_bytes` | `usize` | `1048576` (1 MiB) |
| `max_response_bytes` | `usize` | `4194304` (4 MiB) |
| `max_args` | `usize` | `256` |
| `max_entities` | `usize` | `100000` |
| `max_events` | `usize` | `100000` |
| `max_generates_per_call` | `usize` | `10000` |
| `max_inflight_calls` | `usize` | `16` |
| `request_timeout` | `Duration` | 5 seconds |
| `rate_limit_requests` | `usize` | `120` |
| `rate_limit_window` | `Duration` | 60 seconds |
| `rate_limit_peers` | `usize` | `4096` |
| `max_ttl` | `Duration` | 24 hours |
| `seed` | `u64` | `0` |

## Build programmatically

```rust
use liveengine::hub::HubConfig;
use std::time::Duration;

let config = HubConfig {
    token: std::env::var("LIVEENGINE_TOKEN")?,
    allowed_remote_hosts: vec!["remote".into()],
    max_hubs: 512,
    max_entities: 50_000,
    max_events: 50_000,
    request_timeout: Duration::from_secs(10),
    max_ttl: Duration::from_secs(60 * 60),
    rate_limit_requests: 240,
    ..HubConfig::default()
};
```

`request_timeout` and `max_ttl` are Rust-only settings; the standalone binary does not expose environment variables for them. The remaining limits and the allowlist have environment equivalents.

## from_env

```rust
pub fn from_env() -> Result<Self, String>
```

It reads:

| Environment variable | Field | Parsing |
| --- | --- | --- |
| `LIVEENGINE_TOKEN` | `token` | required string |
| `LIVEENGINE_ALLOWED_REMOTE_HOSTS` | `allowed_remote_hosts` | comma-separated, trimmed, lowercased, empty entries dropped |
| `LIVEENGINE_MAX_HUBS` | `max_hubs` | integer |
| `LIVEENGINE_MAX_BODY_BYTES` | `max_request_bytes` | integer |
| `LIVEENGINE_MAX_RESPONSE_BYTES` | `max_response_bytes` | integer |
| `LIVEENGINE_MAX_ARGS` | `max_args` | integer |
| `LIVEENGINE_MAX_ENTITIES` | `max_entities` | integer |
| `LIVEENGINE_MAX_EVENTS` | `max_events` | integer |
| `LIVEENGINE_MAX_GENERATE` | `max_generates_per_call` | integer |
| `LIVEENGINE_MAX_INFLIGHT_CALLS` | `max_inflight_calls` | integer |
| `LIVEENGINE_RATE_LIMIT_REQUESTS` | `rate_limit_requests` | integer |
| `LIVEENGINE_RATE_LIMIT_WINDOW_SECONDS` | `rate_limit_window` | integer seconds |
| `LIVEENGINE_RATE_LIMIT_PEERS` | `rate_limit_peers` | integer |
| `LIVEENGINE_SEED` | `seed` | unsigned integer |

`LIVEENGINE_BIND` is read by the binary, not by `HubConfig` (default `127.0.0.1:8787`).

Parse failures produce a message naming the variable, for example:

```text
LIVEENGINE_MAX_HUBS must be a positive integer
LIVEENGINE_RATE_LIMIT_WINDOW_SECONDS must be an integer
LIVEENGINE_SEED must be an unsigned integer
LIVEENGINE_TOKEN must be set
```

A missing optional variable keeps the default.

## Validation

`HubService::new` calls `config.validate()` before building the router. It fails when:

- `token.len() < 24` (bytes, not characters)
- any of `max_hubs`, `max_request_bytes`, `max_response_bytes`, `max_args`, `max_entities`, `max_events`, `max_generates_per_call`, `max_inflight_calls`, `rate_limit_requests`, or `rate_limit_peers` is zero
- `rate_limit_window` or `request_timeout` is zero

Failure returns a `String`:

```text
LIVEENGINE_TOKEN must be at least 24 bytes
hub limits and timeouts must be greater than zero
```

`max_ttl` has no validation in `validate()`; registration enforces `ttlSeconds >= 1` and `ttlSeconds <= max_ttl`. Setting `max_ttl` to zero makes every TTL registration fail.

## Practical guidance

- Set the token from a secret store; never hard-code it.
- Keep `allowed_remote_hosts` empty if you do not use external hubs.
- Raise `max_entities` and `max_events` only with a matching application drain strategy.
- Lower `request_timeout` if callers need fast failure, but remember a handler keeps running after a timeout.
- Set `rate_limit_requests` according to whether the host sits behind a shared proxy; the peer budget is per socket address.
- Use a non-zero `seed` when you need reproducible generated users across restarts.
