The `host` feature exposes `liveengine::hub`, including `HubService`, `HubConfig`, `HubHandler`, `HubRegistration`, and `HubMode`. It is enabled by default.

## Mount in Axum

```rust
use liveengine::hub::{HubConfig, HubService};
use std::net::SocketAddr;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let hubs = HubService::new(HubConfig::from_env()?)?;
    let app = axum::Router::new().merge(hubs.router());

    let listener = tokio::net::TcpListener::bind("127.0.0.1:8787").await?;
    axum::serve(
        listener,
        app.into_make_service_with_connect_info::<SocketAddr>(),
    )
    .await?;
    Ok(())
}
```

`HubService::router()` owns these routes:

```text
GET    /health
GET    /v1/contract
GET    /v1/contract/schema
GET    /v1/hubs
POST   /v1/hubs
GET    /v1/hubs/{id}
DELETE /v1/hubs/{id}
POST   /v1/hubs/{id}/call
POST   /v1/registries/import
```

It applies the body limit and the authentication/rate/timeout middleware. Merge it after your application routes, or nest it deliberately and account for the prefix in external addresses.

<Warning>
Use `into_make_service_with_connect_info::<SocketAddr>()`. Without connect info, the host cannot see the socket peer and falls back to a shared `"unavailable-peer"` budget key.
</Warning>

If you nest the hub router under a path prefix, remote clients must include that prefix in their base address. The router itself does not rewrite paths.

## Register an internal handler

```rust


#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    use liveengine::hub::{
        HubConfig, HubHandler, HubMode, HubRegistration, HubService,
    };
    use serde_json::{json, Value};

    struct Echo;

    impl HubHandler for Echo {
        fn call(&mut self, method: &str, args: Vec<Value>) -> Result<Value, String> {
            Ok(json!({ "method": method, "args": args }))
        }
    }

    let service = HubService::new(HubConfig::from_env()?)?;

    let registration: HubRegistration = serde_json::from_value(json!({
        "id": "echo",
        "mode": "internal",
        "scopes": { "kind": "echo" }
    }))?;

    service.register_internal(registration, Echo).await?;
    Ok(())
}
```

`register_internal` returns `Result<HubInfo, String>` and:

- requires `mode: "internal"`
- validates ID, scopes, and optional `scopeSchema`
- rejects `address`, `remoteHubId`, and `remoteToken`
- accepts `ttlSeconds` in `1..=max_ttl`
- rejects duplicates and a full registry

Registration through HTTP (`POST /v1/hubs` with `mode: "internal"`) creates an `Engine` automatically. There is no API to attach an arbitrary handler over HTTP; custom handlers must be compiled into the service.

## HubHandler

```rust fragment
pub trait HubHandler: Send {
    fn call(&mut self, method: &str, args: Vec<Value>) -> Result<Value, String>;

    fn preflight(
        &mut self,
        _method: &str,
        _args: &[Value],
        _config: &HubConfig,
    ) -> Result<(), String> {
        Ok(())
    }
}
```

- `call` runs on a blocking worker; keep it free of long async awaits because it is synchronous.
- `preflight` runs before `call` under the handler lock. Default is `Ok(())`.
- A preflight error becomes `413`.
- A call error becomes `400`.
- A panic becomes `500`; a poisoned lock becomes `503`; a concurrent call that cannot acquire the lock becomes `409`.
- `Engine` implements `HubHandler`, so engine hubs and custom hubs share the same transport, limits, and event/result checks.

See [Host a custom in-process handler](/guides/custom-handler) for a full counter example and container packaging.

## HubService API

```rust fragment
pub struct HubService { /* cloneable Arc state */ }

impl HubService {
    pub fn new(config: HubConfig) -> Result<Self, String>;
    pub fn router(&self) -> axum::Router;
    pub async fn register_internal<H>(
        &self,
        registration: HubRegistration,
        handler: H,
    ) -> Result<HubInfo, String>
    where
        H: HubHandler + 'static;
    pub async fn register(&self, spec: HubSpec) -> Result<HubInfo, String>;
    pub async fn register_hosted(&self, spec: HubSpec) -> Result<HostedHub, String>;
    pub fn register_verifier<V: AuthVerifier>(&self, name: &str, verifier: V) -> Result<(), String>;
    pub fn verify_ticket(&self, ticket: &str, hub_path: &[String], room: &str) -> Result<TicketClaims, &'static str>;
    pub async fn initialize_state(&self) -> Result<(), String>;
}
```

- `register` registers a hub with the same validation as the HTTP API, from a `HubSpec` (which can carry `channels`, `auth`, `schema_ref`, `max_hubs`, `live_depth`, `template`). It refuses a spec with `hosting`.
- `register_hosted` creates a provider-hosted central and returns the hub-scoped credential once. See [provider hosting](/guides/provider-hosting).
- `register_verifier` registers a compiled `liveengine::auth::AuthVerifier` that hubs name with `{ "kind": "custom", "name": "..." }`. See [custom auth](/guides/custom-auth).
- `verify_ticket` verifies and consumes a room ticket.
- `initialize_state` creates or verifies the durable snapshot before the service accepts requests.

`HubService` is cloneable and cheap to share. `HubService::new` validates the config, builds the outbound client with redirects disabled, and creates the in-flight semaphore.

## DTOs

The Rust types serialize with camelCase field names:

```rust
use liveengine::hub::{HubMode, HubRegistration};
use serde_json::json;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let registration: HubRegistration = serde_json::from_value(json!({
        "id": "remote-ranked",
        "mode": "external",
        "address": "https://remote.example.net",
        "remoteHubId": "ranked-au",
        "remoteToken": "a-remote-secret-at-least-24-bytes",
        "scopes": { "region": "au" },
        "ttlSeconds": 3600
    }))?;

    assert_eq!(registration.mode, HubMode::External);
    Ok(())
}
```

`HubRegistration` uses `deny_unknown_fields`, matching the HTTP JSON parser. Unknown fields are rejected.

## Native ping

The host exposes an unauthenticated `GET /v1/ping` route. Rust clients can use `ping_hub`, which measures round-trip time with `Instant` and returns min, average, max, and jitter:

```rust
use liveengine::hub::ping_hub;
use std::time::Duration;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let stats = ping_hub("http://127.0.0.1:8787", 5, Duration::from_secs(3)).await?;
    println!("{:.3} ms avg, {:.3} ms jitter", stats.avg_ms, stats.jitter_ms);
    Ok(())
}
```

`PingStats` serializes with camelCase field names and includes the individual `samples` plus the last `serverTimeMs`.

The standalone binary exposes the same function as a command:

```sh
liveengine-hub ping http://127.0.0.1:8787 --samples 5
liveengine-hub ping http://127.0.0.1:8787 --samples 5 --timeout-ms 3000 --json
```

Running `liveengine-hub` with no command still serves the hub. Use `liveengine-hub serve` explicitly if you prefer.

## Standalone binary

The binary is `src/bin/liveengine-hub.rs`, named `liveengine-hub`, and requires the `host` feature:

```sh
cargo run --locked --release --bin liveengine-hub
cargo install liveengine --bin liveengine-hub
```

It reads `HubConfig::from_env()`, parses `LIVEENGINE_BIND` (default `127.0.0.1:8787`), binds the listener, and serves the router with connect info. Startup failures print to stderr and exit non-zero:

```text
liveengine-hub: LIVEENGINE_TOKEN must be set
liveengine-hub: LIVEENGINE_TOKEN must be at least 24 bytes
liveengine-hub: invalid LIVEENGINE_BIND: ...
liveengine-hub: could not bind 127.0.0.1:8787: ...
```

## Configuration

`HubConfig` controls tokens, allowlists, limits, timeouts, TTL, and the seed. See [Rust configuration](/rust/config) for every field and default, and [Environment reference](/reference/environment) for the standalone variable mapping.

## Operational notes

- Definitions can persist with `HubConfig.state_file`; live engine state remains in memory.
- Registry snapshots are optional; the router does not replicate or elect a leader between processes.
- Outbound calls use the configured request timeout and never follow redirects.
- Remote hosts must be allowlisted before any connection is attempted.
- The response to a timed-out handler does not cancel the handler; reconcile before retrying.

## HTTP client

`liveengine::hub::HubClient::new(address, token)` creates a client for an `http` or `https` hub address with a bearer token. Its public methods:

- `new(address, token)`: validate the address and token and build the client.
- `request(method, route, body)`: send an authenticated request to any `/v1/` route; a 204 response returns null.
- `login(username, password)`: authenticate an account and receive a session token.
- `logout()`: revoke the session used by this client.
- `me()`: retrieve the account that owns this session.
- `change_password(current, next)`: change the session account's password.
- `accounts(method, username, body)`: list or create accounts, or get, update, or delete a named account.
- `connections(hub, room, user)`: list live connections, optionally filtered by hub, room, and user.
- `kick(id)`: disconnect a live connection.
- `route(path, op, body)`: route an operation to a central namespace; an empty path targets the root.
- `discover(body)`: search the hub tree for matching candidates.
- `pair(body)`: pair a subject with a matching target.
- `tree(depth)`: discover hub branches recursively up to the given depth.
- `ticket(path, hub_id, user_id, server_id, role, credential)`: issue a live ticket for a user paired in a room of a hub.
- `watch_ticket(path, depth)`: issue a read-only watch ticket for the live registry.
- `watch(path, depth, on_event)`: subscribe to the live registry over WebSocket and pass each message to `on_event` until it returns `false` or the stream closes.
- `export_registry()`: export public registry definitions without credentials.

Typed wrappers over `request` for the rest of the protocol. Each takes and returns `serde_json::Value` where the shape is yours (scopes, schemas, hub definitions), and a route that answers `204` returns `Value::Null`. Path segments are percent-encoded.

| Method | Route |
| --- | --- |
| `contract()` | `GET /v1/contract`; an error when the protocol is not `HUB_PROTOCOL` |
| `contract_schema()` | `GET /v1/contract/schema` |
| `list_schemas()`, `create_schema(schema)`, `get_schema(reference)`, `delete_schema(reference)` | `/v1/schemas`, `/v1/schemas/{id@version}` |
| `list_templates()`, `create_template(template)`, `get_template(name)`, `delete_template(name)` | `/v1/templates`, `/v1/templates/{name}` |
| `list_hubs()`, `register_hub(definition)`, `get_hub(id)`, `delete_hub(id)` | `/v1/hubs`, `/v1/hubs/{id}` |
| `call_hub(id, method, args)` | `POST /v1/hubs/{id}/call`; returns the call's `result` |
| `import_registry(request)` | `POST /v1/registries/import` with `{ address, token, prefix?, refreshSeconds? }` |
| `list_links()`, `create_link(definition)`, `get_link(id)`, `delete_link(id)` | `/v1/links`, `/v1/links/{id}` ([hub links](/guides/hub-links)) |
| `issue_link_credential(hub_id)`, `revoke_link_credentials(hub_id)` | `POST` and `DELETE /v1/hubs/{id}/link-credentials` |

```rust
use liveengine::hub::HubClient;
use serde_json::json;

async fn link(local: &HubClient, remote: &HubClient, remote_url: &str) -> Result<(), String> {
    remote.register_hub(json!({"id": "far", "mode": "internal"})).await?;
    let credential = remote.issue_link_credential("far").await?;
    local
        .create_link(json!({
            "id": "to-far", "address": remote_url, "remoteToken": credential["token"],
            "hubId": "far", "userId": "bridge", "serverId": "room"
        }))
        .await?;
    println!("{}", local.get_link("to-far").await?["status"]);
    Ok(())
}

#[tokio::main]
async fn main() -> Result<(), String> {
    let token = std::env::var("LIVEENGINE_TOKEN").map_err(|e| e.to_string())?;
    let local = HubClient::new("http://127.0.0.1:8787", token.clone())?;
    let remote = HubClient::new("http://127.0.0.1:8788", token)?;
    link(&local, &remote, "http://127.0.0.1:8788").await
}
```

Errors are `String`s such as `remote: remote returned HTTP 403`. Requests use a five-second timeout (plus any `waitMs` for pairing), no redirects, and a 4 MiB response limit.
