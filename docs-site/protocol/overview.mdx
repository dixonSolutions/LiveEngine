LiveEngine hosts and external hubs share one protocol: **`liveengine.hub/v1`**. The machine-readable schema is served at `GET /v1/contract/schema` and checked into the repository as `docs/hub-contract.schema.json`.

## Base URL and versioning

A hub address is an absolute HTTP(S) base URL with no credentials, query, or fragment. The client appends routes:

```text
http://127.0.0.1:8787/health
http://127.0.0.1:8787/v1/contract
http://127.0.0.1:8787/v1/hubs
```

`GET /v1/contract` is the handshake:

```json
{
  "protocol": "liveengine.hub/v1",
  "version": 1,
  "endpoints": [
    "/health",
    "/v1/ping",
    "/v1/contract",
    "/v1/hubs",
    "/v1/hubs/{id}",
    "/v1/hubs/{id}/call",
    "/v1/registries/import"
  ],
  "schema": "/v1/contract/schema"
}
```

Clients should verify `protocol` before using the service. LiveEngine's `HubClient.contract()` does this automatically and throws `Incompatible hub protocol` on a mismatch.

## Authentication

- `GET /health` and `GET /v1/ping` are unauthenticated.
- Every other HTTP endpoint requires `Authorization: Bearer <token>`. The WebSocket endpoints `/v1/live` and `/v1/live/registry` authenticate in their first frame instead.
- The token is the host's `LIVEENGINE_TOKEN` and must be at least 24 bytes at startup.
- Authentication is administrative, not per-player. Browsers connect to the live sockets with single-use tickets that your server obtains, and a hub's `auth` can verify a user credential before a ticket is issued. Two narrower bearer credentials exist, each for one route: a hub link credential and a hub-scoped provider credential.
- Requests without a valid token return `401` with `{"error":"unauthorized"}`.

Requests other than `/health` and `/v1/ping` are rate-limited by socket peer **before** checking the token. An unauthenticated request to those routes still consumes a rate slot.

## Content type and JSON

Request bodies use `Content-Type: application/json`. Responses are JSON except `204 No Content` on delete. Unknown fields in registration, call, and import DTOs are rejected because the Rust types use `deny_unknown_fields`.

```json
{ "method": "upsertUser", "args": [ { "id": "alice" } ] }
```

```json
{ "result": true }
```

Application method results are wrapped in `result`; the Node `HubClient.call` unwraps it for you.

## Route map

| Method | Route | Auth | Purpose |
| --- | --- | --- | --- |
| `GET` | `/health` | no | Liveness, protocol, uptime |
| `GET` | `/v1/contract` | yes | Capability handshake |
| `GET` | `/v1/contract/schema` | yes | Embedded JSON schema |
| `GET` | `/v1/hubs` | yes | Discover attached hubs |
| `POST` | `/v1/hubs` | yes | Register an internal or external hub |
| `GET` | `/v1/hubs/{id}` | yes | Inspect one hub |
| `DELETE` | `/v1/hubs/{id}` | yes | Remove a registration |
| `POST` | `/v1/hubs/{id}/call` | yes | Exchange method/args for a result |
| `POST` | `/v1/registries/import` | yes | Import or refresh a remote registry |
| `GET` | `/v1/registry/export` | yes | Export public definitions |
| `POST` | `/v1/route` | yes | Route an operation into a central namespace |
| `GET` | `/v1/tree` | yes | Discover nested branches |
| `GET`, `POST` | `/v1/schemas` | yes | List or publish schemas |
| `GET`, `DELETE` | `/v1/schemas/{id}` | yes | Read or delete a schema |
| `GET`, `POST` | `/v1/templates` | yes | List or create templates |
| `GET`, `DELETE` | `/v1/templates/{name}` | yes | Read or delete a template |

See [Endpoints](/protocol/endpoints) for bodies and status codes, and [Registration DTOs](/protocol/registration) for field rules.

## Error format

Errors are always:

```json
{ "error": "human-readable message" }
```

Validation messages are intended for diagnostics. Do not depend on exact wording across versions; branch on HTTP status and, for engine results, on the structured `ok` and `reason` fields.

## Hub IDs

IDs and remote hub IDs:

- 1–128 characters
- ASCII letters, digits, `.`, `_`, `-`
- not `.` or `..`
- no leading or trailing whitespace

The prefix for registry imports is at most 64 characters of the same character set.

## TTL

`ttlSeconds` is optional, at least 1, and at most `max_ttl` (default 24 hours). Expired registrations are removed by a background reaper.

## Schemas and forwarding

Schemas use JSON Schema 2020-12. Only local JSON pointer references are supported; remote references, IDs, anchors and cycles are rejected. A hub accepts `scopeSchema` or `schemaRef`, with optional `userSchema` and `serverSchema`; inherited schemas apply to nested children. Schema-bound hubs reject `generateUsers`.

Forwarding uses `x-liveengine-trace` and `x-liveengine-depth`. Repeated instance IDs and depth exhaustion return 508. `LIVEENGINE_MAX_DEPTH` defaults to 8 and is capped at 16. Clients should not set forwarding headers. Registry definitions can be persisted using `LIVEENGINE_STATE_FILE`; live rooms and players remain in memory. See [nesting](/guides/nesting) and [schemas](/guides/schemas).
