title: "Internal hubs, external hubs, and registries"
description: "How the registry attaches internal engines and remote services, how TTL and hop limits work, and what imports actually copy."
---

A host process owns a registry of hubs. Each registration has a local **hub ID**, a mode, scopes, optional `scopeSchema`, optional TTL, and — for external hubs — a remote address, remote hub ID, and remote credential.

## Internal hubs

- `mode: "internal"` with an HTTP registration creates a fresh `Engine` inside the host.
- The hub ID is both the local registry key and the default remote hub ID.
- Calls run on a blocking worker so a long matchmaking operation does not stall the async runtime.
- Custom internal hubs are compiled into the Rust service with `HubService::register_internal`; they are not loaded dynamically over HTTP.

```json
{
  "id": "ranked-au",
  "mode": "internal",
  "scopes": { "game": "chess", "region": "au" },
  "scopeSchema": {
    "type": "object",
    "required": ["region"],
    "properties": { "region": { "type": "string", "enum": ["au", "nz"] } },
    "additionalProperties": false
  },
  "ttlSeconds": 3600
}
```

Internal registrations must not include `address`, `remoteHubId`, or `remoteToken`.

## External hubs

An external registration attaches an independently hosted service at its own address:

```json
{
  "id": "remote-ranked",
  "mode": "external",
  "address": "https://remote.example.net",
  "remoteHubId": "ranked-au",
  "remoteToken": "a-separate-remote-secret-at-least-24-bytes",
  "scopes": { "region": "au" },
  "ttlSeconds": 3600
}
```

At registration time the central host:

1. Validates the address and checks the destination host against `LIVEENGINE_ALLOWED_REMOTE_HOSTS`.
2. Calls the remote `GET /health` and requires `protocol === "liveengine.hub/v1"`.
3. Calls the remote `GET /v1/contract` and checks the same protocol.
4. Calls the remote `GET /v1/hubs/{remoteHubId}` and requires the hub to exist.

If any step fails, registration returns `502` and no local registration is created. Forwarded calls use `POST /v1/hubs/{remoteHubId}/call` with the same `{ method, args }` body and `{ result }` response as internal calls, authenticated with the **remote** token. The remote credential is never returned by list, get, or import responses.

Removing an external registration does not remove or stop the remote hub. It only removes the local route.

## Registry discovery

`GET /v1/hubs` returns public metadata for every live registration, sorted by ID:

```json
{
  "hubs": [
    {
      "id": "ranked-au",
      "mode": "internal",
      "remoteHubId": "ranked-au",
      "scopes": { "game": "chess", "region": "au" },
      "scopeSchema": { "type": "object" },
      "expiresInSeconds": 3540
    }
  ]
}
```

`GET /v1/hubs/{id}` returns one record or `404`. `expiresInSeconds` is recomputed from TTL when the record is read. Expired records are removed lazily on registry access.

## Expiry, imports and persistence

Hubs can expire with `ttlSeconds`. Templates provide defaults, `ifAbsent` permits idempotent creation, and local centrals can set a `maxHubs` child quota. Imports are snapshots unless `refreshSeconds` enables periodic refresh; missing source entries become stale rather than being deleted.

Set `LIVEENGINE_STATE_FILE` to persist definitions, schemas, templates, imports, credentials and instance ID. The file is created mode 0600 and rejected if group or world accessible; protect backups too. Live players and rooms remain in memory. See [hosting](/guides/hosting).

## Nesting and schemas

A central is a namespace, either local or backed by another service. Route operations through a path of central IDs; tree discovery reports branch errors without failing the entire listing. Forwarding is bounded by `LIVEENGINE_MAX_DEPTH` (default 8, maximum 16), and repeated instance IDs in the trace return 508. See [nested hubs](/guides/nesting).

Schemas use JSON Schema 2020-12 with local JSON pointer references. Hubs can use an inline `scopeSchema` or immutable `schemaRef`, and override user and server schemas separately. Nearest central schemas are inherited. Schema-bound hubs reject `generateUsers`; submit validated users instead. See [schemas](/guides/schemas).
