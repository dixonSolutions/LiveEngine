---
title: "Gogh Strike integration"
description: "Real multiplayer for Gogh Strike through a bridge that pairs players with a hub and a LiveClient in the browser, plus the bridge tests."
---

The integration connects [petergpt/gogh-strike](https://github.com/petergpt/gogh-strike) to LiveEngine. The browser talks only to a Node bridge. The LiveEngine administrative token and any remote credential stay in the Node process and never reach browser code or URLs.

Players who choose **Find a LiveEngine match** are paired into one hub room and see each other move, shoot and die. Each client keeps its own simulation and bots; player state travels at 20 Hz on a lossy `state` channel, and shots, hits and deaths on a reliable `event` channel.

## What it does

- Applies a lobby and networking patch to an upstream Gogh Strike checkout. The game holds only its DTOs, schemas and the mapping to and from game state (`src/liveengine-net.js`).
- Serves the game and mounts the generic [hub API](/guides/hub-api) (`lib/hub-api.mjs`) with Gogh Strike's schemas, channels and scopes. `bridge.mjs` holds only that wiring and the static file server.
- Adds a **Play online** panel to the lobby: a hub API address (this page's origin by default, remembered), **Connect**, a live status line with ping and players waiting, the live hub list, and **Find match** with a cancel. The hub API may be on another origin.
- On first use registers the game's schemas and the hub's channels, and a hub `auth` verifier when `GOGH_HUB_AUTH` is set.
- Connects, retries, renews tickets and falls back from WebRTC to the hub relay inside `LiveClient`, not in the game.
- Optionally routes through an external hub registered on a central service.

## What it does not do

- No shared bots or scoreboard: each client simulates its own bots, and scores are tallied per client.
- No browser-facing LiveEngine token.
- No remote device claim; the recorded tests ran against local services.
- No automatic installation of the upstream game or Playwright.
- No browser run of the multiplayer version has been recorded yet.

## Prerequisites

Clone the upstream game beside the LiveEngine repository:

```sh
git clone https://github.com/petergpt/gogh-strike ../gogh-strike
```

The validated upstream commit is `2285e640097d9b12bcc42af72d5e8d0b37082f51`.

Apply the patch once:

```sh
patch="$PWD/integrations/gogh-strike/gogh-strike.patch"
if git -C ../gogh-strike apply --check "$patch"; then
  git -C ../gogh-strike apply "$patch"
else
  git -C ../gogh-strike apply --reverse --check "$patch"
fi
```

The `else` branch accepts a checkout where the patch is already applied.

## Run the bridge

```sh
LIVEENGINE_URL=http://127.0.0.1:8787 \
LIVEENGINE_TOKEN=your-local-token \
LIVEENGINE_HUB_ID=gogh-strike \
GOGH_STRIKE_ROOT=../gogh-strike \
node integrations/gogh-strike/bridge.mjs
```

Open `http://127.0.0.1:8967/`, select **Find a LiveEngine match**, then press **Play**.

The bridge validates Host and Origin, limits request bodies to 16 KiB, and rate-limits joins. It has no player authentication. The upstream game's own `npm start` does not include the proxy; use the bridge command so credentials are not placed in browser storage.

## Hosting on a network

By default the bridge binds to `127.0.0.1`. To serve the game over a trusted LAN, bind the LAN address and keep the allowlist narrow:

```sh
HOST=192.168.1.10 PORT=8967 \
LIVEENGINE_URL=http://127.0.0.1:8787 \
LIVEENGINE_TOKEN=your-local-token \
LIVEENGINE_HUB_ID=gogh-strike \
GOGH_STRIKE_ROOT=../gogh-strike \
node integrations/gogh-strike/bridge.mjs
```

A concrete `HOST` is allowed automatically alongside loopback. If you bind `0.0.0.0` or use several addresses, list them explicitly:

```sh
HOST=0.0.0.0 \
GOGH_ALLOWED_HOSTS=192.168.1.10:8967 \
GOGH_ALLOWED_ORIGINS=https://gogh.example.net \
node integrations/gogh-strike/bridge.mjs
```

<Warning>
  The bridge has no player authentication. Expose it only on a trusted LAN, or put an authenticated proxy in front of it. Do not publish it directly to the Internet.
</Warning>

<Note>
  The lobby generates client IDs with `crypto.getRandomValues`, so matchmaking works over plain HTTP on a LAN where `crypto.randomUUID` is unavailable.
</Note>

### Bridge configuration

| Variable | Default | Purpose |
| --- | --- | --- |
| `LIVEENGINE_URL` | none (required for matchmaking) | HTTP base URL of the hub service |
| `LIVEENGINE_TOKEN` | none (required for matchmaking) | Administrative token for the hub service |
| `LIVEENGINE_HUB_ID` | `gogh-strike` | Local hub ID to create or use |
| `LIVEENGINE_HUB_MODE` | `internal` | `internal` or `external` |
| `LIVEENGINE_REMOTE_ADDRESS` | empty | Remote base URL for an external registration |
| `LIVEENGINE_REMOTE_HUB_ID` | `LIVEENGINE_HUB_ID` | Remote hub ID |
| `LIVEENGINE_REMOTE_TOKEN` | empty | Remote credential (at least 24 bytes) |
| `GOGH_STRIKE_ROOT` | `../gogh-strike` relative to repo | Game checkout |
| `HOST` | `127.0.0.1` | Bind address |
| `PORT` | `8967` | Bridge listen port |
| `GOGH_ALLOWED_HOSTS` | empty | Extra allowed `host:port` values for Host checks |
| `GOGH_ALLOWED_ORIGINS` | empty | Extra allowed `scheme://host:port` origins |
| `GOGH_MATCH_SERVER_ID` | `gogh-strike-local` | Room ID |
| `GOGH_MATCH_CAPACITY` | `12` | Room capacity |
| `GOGH_HUB_AUTH` | empty | JSON of a hub `auth` verifier; players then need a credential |
| `GOGH_REQUEST_LIMIT` | `10` | Requests per client address per minute, across all API routes |

For an external hub:

```sh
LIVEENGINE_URL=http://127.0.0.1:8787 \
LIVEENGINE_TOKEN="$LIVEENGINE_TOKEN" \
LIVEENGINE_HUB_ID=gogh-strike \
LIVEENGINE_HUB_MODE=external \
LIVEENGINE_REMOTE_ADDRESS=http://127.0.0.1:8788 \
LIVEENGINE_REMOTE_HUB_ID=gogh-strike \
LIVEENGINE_REMOTE_TOKEN="$LIVEENGINE_REMOTE_TOKEN" \
GOGH_STRIKE_ROOT=../gogh-strike \
node integrations/gogh-strike/bridge.mjs
```

The central service must allow the remote host and use matching credentials on the remote service.

## Bridge endpoints and limits

These are the hub API's routes, mounted at `/api/liveengine`; `GET /api/liveengine/ping` and `GET /api/liveengine/live-client.mjs` are also served.

| Route | Behavior |
| --- | --- |
| `GET /health` | `{ app, hubId }` |
| `GET /api/liveengine/status` | Configuration status; does not require a working hub |
| `POST /api/liveengine/pair` | `{userId, team, role, credential?}`: returns the descriptor `{link, room, userId, ticket, url, transports}` for `LiveClient` |
| `POST /api/liveengine/renew` | `{userId, credential?}`: a fresh descriptor for a player who paired; `404` otherwise |
| `POST /api/liveengine/discover` | `{kind?, depth?, requirements?}`: candidates under the configured hub path |
| `POST /api/liveengine/watch` | `{depth?}`: a read-only registry watch ticket and the registry URL, for a live hub list in the page |
| `POST /api/liveengine/join` | The older seat-only matchmaking call; `leave` and `heartbeat` apply to both |
| `GET /liveengine/live-client.mjs` | `lib/live-client.mjs` for the browser |

The bridge:

- validates the `Host` header against loopback, the concrete `HOST:PORT`, and `GOGH_ALLOWED_HOSTS`
- validates the `Origin` header on join requests against the allowed hosts and `GOGH_ALLOWED_ORIGINS`
- limits request bodies to 16 KiB
- rate-limits API calls to 10 per 60 seconds per socket peer (`GOGH_REQUEST_LIMIT`)
- returns `503` when `LIVEENGINE_URL` or `LIVEENGINE_TOKEN` is missing
- returns `409` when matchmaking returns `ok: false`, and `400` for invalid input
- propagates an upstream HTTP status (for example `401`) when one is available, otherwise returns `502`

`userId` must match `^[a-zA-Z0-9_-]{1,64}$`. Team is `0` or `1`; role is truncated to 40 characters.

## Peer-to-peer play

By default every player joins the hub's shared room and traffic uses the relay. Set `GOGH_LIVE_LINK=peer` to pair players with each other: the first player's request is held (up to `GOGH_PEER_WAIT_MS`, default 30000, then `408`) until another player pairs with them. Both get a `peer-peer` descriptor, so `LiveClient` opens a WebRTC data channel with the hub as signalling and fallback. The game sets `directBroadcast` so its player state uses the data channels. `LIVEENGINE_WATCH_URL` overrides the registry address the `watch` route returns.

## Adapter test

No dependencies are needed:

```sh
npm run test:integration
```

`bridge.test.mjs` uses a fake local HTTP hub and verifies the contract handshake, internal and external registration, the matchmaking call sequence, and rejection of hostile Host and Origin headers. `bridge-live.test.mjs` runs against a real `liveengine-hub` with real WebSockets: schema and channel registration, two players in one room on both channels, schema enforcement, renewal and reconnect, discovery, hub auth, and the administrator token never appearing in a response.

## Local end-to-end test

`npm run test:e2e` runs `live-e2e.mjs`: real hub processes, the real bridge and the real game in headless Chromium, on free loopback ports, stopped at the end. It covers a central hub, a nested central and an on-demand hub with its own auth (bad and good credentials); peer-peer over WebRTC with the data channel asserted open and carrying frames; a forced fallback to the relay; peer-hub with a service participant; hub-hub across two linked services; reconnect with a fresh ticket; a live hub list from a watch ticket; and schema rejection. It prints one `PASS` or `FAIL` line per scenario and exits non-zero on any failure. Scenarios 9 to 14 drive the lobby's Play online panel (two users, four users, cancel, another origin, a wrong address, the LAN address). It needs `npm run build:hub` and Playwright; the game is fetched and patched automatically (see [Developer testing](/guides/dev-testing)), and `PLAYWRIGHT_PATH`, `CHROMIUM_PATH` and `GOGH_STRIKE_ROOT` override; `GOGH_E2E_CHROMIUM_ARGS` replaces the Chromium flags and `GOGH_E2E_ONLY=2,3` selects scenarios for debugging (the exit code is then non-zero). Chromium gets `--disable-features=WebRtcHideLocalIpsWithMdns --allow-loopback-in-peer-connection` so contexts find local WebRTC candidates, and, when `/dev/dri/renderD128` exists, ANGLE over Vulkan flags so the game renders on the GPU: software GL runs the town at under one frame a second.

## Service end-to-end check

`e2e.mjs` is an opt-in, replayable check against running HTTP services. It reads `LIVEENGINE_TOKEN` or `LIVEENGINE_TOKEN_FILE`. For an external run it also reads `LIVEENGINE_REMOTE_TOKEN` or `LIVEENGINE_REMOTE_TOKEN_FILE`.

```sh
LIVEENGINE_URL=http://127.0.0.1:8787 \
LIVEENGINE_TOKEN_FILE=/path/to/central-token \
LIVEENGINE_HUB_MODE=external \
LIVEENGINE_REMOTE_URL=http://127.0.0.1:8788 \
LIVEENGINE_REMOTE_TOKEN_FILE=/path/to/remote-token \
node integrations/gogh-strike/e2e.mjs
```

With Compose, also set:

```sh
LIVEENGINE_REMOTE_ADDRESS=http://remote:8787
```

The test client reaches the remote through loopback port `8788`, while the central container forwards through the container hostname.

Additional e2e variables:

| Variable | Purpose |
| --- | --- |
| `GOGH_BRIDGE_PORT` | Fixed bridge port; otherwise an ephemeral port |
| `PLAYWRIGHT_PATH` | Path to a Playwright `index.mjs`; enables headless browser coverage |
| `CHROMIUM_PATH` | Optional browser executable |
| `GOGH_SCREENSHOT` | Screenshot path; default `liveengine-gogh-lobby.png` under `TMPDIR` |

The e2e runner creates unique hub/room IDs and removes test hubs afterward. It asserts the remote user is `paired` and the server membership includes the user. With Playwright it checks the lobby checkbox, starts a match, verifies the LiveEngine toast, checks browser user pairing, and records page errors.
